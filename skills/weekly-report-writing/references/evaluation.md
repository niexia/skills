# Evaluation criteria and scenarios

These inputs are independently fictional and contain no real projects or business
data. They support rule walkthroughs; they do not establish independent Agent execution.

## Output checks

| Dimension | Passing condition |
| --- | --- |
| Facts | Every actual development and decision traces to current inputs without invention |
| Time | Period, cutoff, planned and actual dates are distinct; history is not presented as a current update |
| Status | Development, testing, deployment, limited rollout, full rollout and outcome verification are separate |
| Results | Metrics include definitions and baselines; unknown significance or incomparable data is not presented as benefit |
| Organization | Business → area → project; only specified sample sections guide style; duplicates merge and history compresses |
| Actions | Next steps include actions and acceptance criteria without guessed dates or owners |
| Risks | Dependencies and impact are clear; unconfirmed pauses or acceptance are not treated as decisions |
| De-identification | Reusable materials exclude real organizations, projects, people, customers, private links and actual data |

## Scenario 1: Merge duplicate updates

Input: Project A's frontend work is complete and backend integration is complete,
but end-to-end verification continues. The latest confirmation plans release next
period. The project appears in both product and technical sections.

Expected: One project, Testing status. State completed component scope, remaining
end-to-end verification and planned release. Do not claim release or count two projects.

## Scenario 2: Release does not establish outcomes

Input: Project B is released to a small subset of users. Configuration is complete,
but actual use and final outcome reporting are missing. An update calls it effective.

Expected: Released, limited rollout, outcomes pending verification. Next steps
address use and data collection. Do not adopt the unsupported effectiveness claim.

## Scenario 3: Incomparable results

Input: Project C has two user cohorts from different periods with different
configurations. A proxy metric improves for the first; final metrics are missing
for the second. No statistical test is supplied.

Expected: Report observations separately. Do not aggregate benefits or claim the
final goal is achieved. State configuration, period and outcome-reporting gaps.

## Scenario 4: Date conflicts and cutoff

Input: Project D's original plan targets this period, but a newer confirmation
moves it to next period. A post-cutoff update says released. Project E's planned
date has passed with no completion record.

Expected: This period uses the pre-cutoff confirmation and reports the revised
plan. Include later release only in an authorized subsequent supplement.
Mark Project E's actual result for confirmation.

## Scenario 5: Missing dependencies and reading access

Input: Some sources are inaccessible, but supplied text supports known projects.
Owners, some ETAs and screenshot values are missing.

Expected: Finish supported content, identify unverified sources and flag essential
gaps. Do not infer image values or stop all consolidation.

## Scenario 6: Invocation and external writing

Input: The user requests only transcript cleanup, a PRD, or automatic report publication.

Expected: Transcript and PRD tasks do not invoke this skill merely because updates
are mentioned. Publication requires authorization for the target and operation.
Source reading alone does not authorize writing.

## Scenario 7: Business ownership and reference scope

Input: The user specifies only Business A's sample section as the reference.
Current updates cover Businesses A and B, including product work, customer testing
and performance work serving Business A. The sample also has a global stability chapter.

Expected: Learn the specified section only. Update each business separately,
grouping projects by area. Place performance work under Business A and tests under
their corresponding project. Do not add unspecified sample chapters or global
stability and action tables.

## Metric edge cases

Metric edge case: With a zero target or baseline, do not calculate attainment
or relative growth. Report supplied values and the undefined calculation.
With rates changing from 20% to 25%, report +5 percentage points or +25%
relative change, keeping the two definitions distinct.
